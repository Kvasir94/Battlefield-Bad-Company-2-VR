# XM8 VR bolt carrier group: runtime integration (2026-10-09)

This change brings the asset lane's authored XM8 bolt into the build
(`reports/xm8-bolt-intake/HANDOFF.md`). The bolt is drawn on the player's own
first-person XM8. The flat `jntWpn_4` port card is collapsed while the bolt draws.
The left hand can rack the charging handle.

**Scope: presentation plus gating only.** No native completion hook has been
identified for the XM8, so none is guessed. The handle stroke never chambers a
round, never touches ammunition, timers or native state, and never calls
`WeaponCycle::Complete`. No game launch, GPU capture or headset run was done for
this change.

## Switches and asset path

| Variable | Default | Effect |
|---|---|---|
| `FVR_XM8_BOLT` | on | `0` disables everything: no load, draw, palette edit or cycle. |
| `FVR_XM8_BOLT_ASSET` | unset | Absolute path to the render-input JSON. It overrides the search. |

- **Default search.** The loader looks for
  `reports/xm8-bolt-intake/xm8-bolt-v1-render-input.json`. It walks up to five
  parents from the session report folder, then from the probe DLL folder
  (`<repo>/build/x86`). The launcher's repository root is therefore found
  without configuration.
- **Validation receipt.** It is read next to the render input, using the file
  name from the render input's `validation` field (`xm8-bolt-v1-validation.json`).
- **Not committed.** Both files are game-derived (native rig binds) and stay out
  of git. `/reports/` in `.gitignore` covers them; `git check-ignore` confirms
  both paths.
- **Environment.** Like the other `FVR_*` switches, a variable must be in the
  environment that starts BC2. The probe is injected into that process.
- **Fail soft.** If the asset is missing or invalid, the feature stays off and
  the game is unchanged. The reason is reported in the native report under
  `"xm8_bolt"`, as `asset_status` and `detail`. Statuses are `loaded`,
  `disabled`, `not_found`, `read`, `json`, `schema`, `rig`, `part`, `geometry`,
  `validation`, `validation_mismatch` and `exception`.

## Components

| File | Role |
|---|---|
| `Bc2Xm8BoltAsset.{h,cpp}` | JSON parse, SHA-256, conversion to carrier-local canonical metres, validation |
| `Bc2Xm8BoltPresentation.{h,cpp}` | Rig binding, travel transform, card-collapse decision, both-eye draw latch |
| `Bc2Xm8BoltCycle.{h,cpp}` | `WeaponCycle` Pump profile and the left-hand arbiter adapter |
| `Bc2Xm8BoltRuntime.{h,cpp}` | In-process owner (probe DLL only): configure, publish, draw, report |

Glue lives in three files:

- **`Bc2RigPublication.cpp`, `PoseXm8Bolt`.** Runs once per retargeted pose.
  It publishes the posed carrier and collapses the card in that palette.
- **`NativeProbe.cpp`.** Configures the runtime, draws at the post-eye boundary,
  and handles stop/pump and the report.
- **`Bc2Gameplay.cpp`.** Ticks the cycle beside the magazine lane. It masks
  Fire and AlternateFire, marks the left hand busy for support grip, and
  feeds handle travel.

## Checked (code and data verified in this change)

- **Rig fingerprint.** The asset rig's names, parents and canonical inverse
  binds hash to `0xa7f219a1426216ab` with the same `SightRigFingerprint`
  runtime code. Conversion matches `Bc2Rig.cpp` bit for bit. The declared
  `fnv1a64:a7f219a1426216ab` string matches as well.
- **Receipt.** The render input's SHA-256 equals the receipt's `export.sha256`
  (`b48b810f…a83a`). The loader also requires the receipt's topology flags:
  all triangles, closed manifold, 0 boundary/non-manifold/degenerate, 1 shell,
  outward normals. It requires the vertex and triangle counts (52/100), the
  single rigid joint, the travel axis and the stroke to match.
- **Independent geometry checks.** The loader re-checks the geometry itself.
  Every edge is shared by exactly two oppositely wound faces. No triangle is
  degenerate. Each converted face normal agrees (dot > 0.99) with the asset's
  reflected `geometric_normal`.
- **Conversion.** Each archive point is reflected in Z, then moved into the
  carrier frame by the canonical inverse bind. Corner order is reversed. This
  is `ExtractRigidProp`'s `NativeRightHanded` rule. The converted bounds match
  the receipt's canonical forward bounds minus the carrier rest
  (0, 0.069722, −0.38314) to within 0.2 mm. This is a CPU test with the real
  file, run via `FVR_XM8_BOLT_ASSET`.
- **Card collapse.** It reuses `CollapseWeightedPalette`, the same edit that
  hides the magazine. Only `jntWpn_4`'s 12 consumed skin scalars are zeroed.
  All other entries and all padding bytes are unchanged. The colour pass and
  the ZOnly pass consume the same packed palette, as do both eyes. One decision
  per published pose therefore covers colour, depth and both eyes.
- **Draw source.** The bolt is drawn at `jntWpnwpnJnt_16`'s final written
  transform. That transform is the retargeted weapon subtree, plus any handle
  travel the existing charging-handle presentation wrote. The bolt is drawn only
  when the right hand is tracked and the weapon subtree is in the private
  palette. That is the same condition that allows the card collapse.
- **Safety.** No new native call, hook, vtable call or game-memory write. The
  only state edited is the existing private first-person palette copy for the
  player's own rig, through the existing PackHook path. D3D work uses the
  existing `D3D11RigidPropRenderer` on the graphics thread that owns it.

## Inferred or design choices (not native evidence)

- **Draw path.** The bolt uses the in-game dropped-magazine draw path. It draws
  after that eye's native draw returns, into the bound RTV, with depth tested
  against the bound DSV and never written. That path has prior both-eye evidence
  for world props (run 190842). The 1P weapon's depth in that DSV is not proven.
  The bolt relies on the receiver shell occluding it, apart from the port.
- **Not native shading.** The bolt is not drawn in the `jntWpn_12_FlatMetal`
  section, palette or material. That would need verified 64/32-byte record
  semantics, a section-local palette map and a native draw injection, none of
  which exist yet. The bolt is a flat dark-metal colour (0.16, 0.16, 0.17) with
  the renderer's simple normal shading. It is drawn after post-processing, so
  scene lighting and tonemapping do not apply to it.
- **Card latch.** The card collapses only after both eyes of a recent frame drew
  the bolt (250 ms latch). Any failed or stale eye drops the latch immediately.
  The next palette then shows the native card again, which hides the bolt.
  Expect a one-frame card-visible start and at most about one frame of mismatch
  at transitions.
- **Travel.** Hand travel reuses the existing `handleTravel` presentation in rig
  publication (`FindChargingHandleParts`: carrier plus handle, native local
  plus Z travel, 60 ms spring back). There is no second writer for joints 16
  and 17. The baseline is therefore the native current local, not the asset rest
  frame. The two are identical in the idle, reload and FireStart t=0 poses.
  Native FireStart moves the carrier 119.9 mm, and the bolt follows it while
  firing.
- **Cycle contract.** The asset lane's numbers: Pump family, axis {0,0,+1},
  stroke 0.119885 m, grab point (0, 0.069722, −0.496687). Rear 10 mm, front
  8 mm, lateral 30 mm, contact radius 60 mm and max step 70 mm are proposed UX
  defaults. Rotation tolerance (0.5 rad) and dwell (20 ms) are my defaults.
- **Grasp point.** The hand's grasp point uses the same palm offset as the
  existing rack: the magazine profile's `insertion.itemFromHand`. This offset
  has not been calibrated for the handle.
- **Lease.** The `WeaponCycleLease` is a VR presentation lease. It names the
  stroke only and is not a native held-cycle receipt. A finished
  rear-then-forward stroke reaches `AwaitingNative` and is retired at once as
  "presentation complete" (counted in the report).

## Interaction gating

- **Hover.** A neutral left hand within 60 mm of the handle opens an
  `AwaitingGrip` cycle. It takes no claim and blocks nothing.
- **Grab.** A fresh squeeze in range acquires a left Mechanism claim through
  the shared arbiter. The claim depends on the right GunHold and uses the raw
  contact's own input packet as evidence. It never steals a held claim (support,
  sight, ammo). A refused attempt needs a release before another try.
- **Exclusive with the magazine lane.** The cycle never starts, and a running
  stroke is cancelled, while the magazine lane holds the hand or owes its own
  chamber rack. Owes means `rackTravel >= 0` or `rackOwnsLeft`. It also yields
  while magazine work blocks weapon actions. The existing post-empty rack keeps
  sole ownership of that case.
- **While held.** Fire and AlternateFire are masked. Support grip treats the
  left hand as busy. The carrier and handle follow the hand along the axis.
- **Ending.** Release, leaving the rail (lateral, step or rotation), losing the
  claim, switching weapon or any lane cancel ends the stroke. The handle springs
  back.

## Tests (CPU only)

`Bc2Xm8BoltTests` has 12 groups:

- SHA-256 vectors.
- Synthetic asset parse and conversion.
- Fail-soft rejections: export hash, open receipt, counts, stroke, open mesh,
  blended weights, flipped normal, schema, truncated JSON, wrong rig, declared
  fingerprint, missing file.
- Path resolution and the `FVR_XM8_BOLT` switch.
- Travel transform.
- Rig binding and the card-collapse decision with a byte-exact collapse.
- Both-eye draw latch.
- Cycle profile contract.
- A full hover, grab, stroke and presentation-complete run through the real
  `HandInteraction`.
- Exclusivity with the magazine lane and support.
- Fresh-grip and cancel paths.
- The real asset, when `FVR_XM8_BOLT_ASSET` is set.

These suites also pass on the same build: `WeaponCycleTests`,
`Bc2PumpPartTests`, `WeaponModeTests`, `Bc2AuthoredGripTests`,
`PhysicalWeaponStateTests`, `ControllerInputTests`, `Bc2WeaponVisibilityTests`,
`Bc2MagazinePhysicalTests` and `RigPoseTests`.

## What the headset test should look for

1. **Report.** `"xm8_bolt"` shows `asset_status: loaded` and `active: true`.
   `draw.drawn` grows, with `failed`, `stale` and `backend` near 0 and
   `healthy: true` while the XM8 is held. `card.collapse` dominates over
   `renderer_unproven`.
2. **Ejection port, both eyes.** The port shows the carrier side, the octagonal
   bolt head and the cam pin, not the flat card. Close one eye at a time; the
   result must be identical. A hole into the empty pocket means the card
   collapsed without a drawn bolt; check `draw.failed`/`stale`.
3. **Occlusion.** Only the port region of the bolt should be visible. If the
   whole carrier shows through the receiver or the top rail, the 1P weapon is
   not in the bound depth. The fix is then a native in-section draw, not this
   path. Report it with eye screenshots.
4. **Shading.** Expect the bolt to look flatter and darker than the gun. Note
   whether that is acceptable or needs the native FlatMetal section.
5. **Firing.** On full auto the bolt should move with the native carrier
   animation, along with the rod and handle. Check for z-fighting or lag at the
   port edges.
6. **Racking.** With the left hand free, squeeze at the charging handle, which
   sits under the front of the carry handle.
   - The handle and carrier follow the hand rearward (about 120 mm) and back.
   - The trigger does nothing while you hold it.
   - Release or a twist cancels the stroke and the handle springs back.
   - Holding support grip must still work: grab the handle only after
     releasing support.
   - After an empty reload, the existing post-empty rack (magazine lane) should
     still own the handle. This cycle must not interfere with it.
7. **Kill switch.** With `FVR_XM8_BOLT=0` the gun looks native: the card is
   visible, there is no bolt draw, and the handle cannot be racked unless the
   magazine lane's rack is owed.

## Remaining

- **Native completion hook.** None is identified (fltAutomaticFire,
  `BoltActionTime 0`). Find a native charge/chamber boundary, for example the
  empty-reload completion, before the stroke can mean anything to the game.
- **Native drawing.** A native in-section draw (FlatMetal material, real UV
  layout, ZOnly entry) needs the verified record-tail semantics and the
  section-local palette map from NATIVE-DRAW-CONTRACT.md.
- **Hand pose.** Left-hand finger pose and a grasp offset for the handle; no
  hand attachment is authored.
- **Tuning.** Headset tuning of the contact radius and the lateral and
  rotation tolerances.

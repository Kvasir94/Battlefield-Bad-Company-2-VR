## What fixed the drop to the main menu

The M9's `SoldierWeaponData` had no network id in the process-wide table `[0x156d500]`. The client then
could not decode the soldier ghost and closed the connection (reason 6), and the UI went from state 4
(leave level) to state 0 (main menu).

`TestRange.RegisterNetIds 1` checks each given weapon with `0x5debd0` and registers it with `0x5e5d70`
before the native give.

## Invisible 1P M9: solved (17:30)

The cause was missing shaders, not animation. MP weapon materials (`US_hg_M9Beretta/Shaders/...`,
`US_rif_XM8c/Shaders/...`) exist only in MP levels' shader databases (`Levels/<L>/Shaders/Dx11_Single.res`).
SP_02's database has none of them, and mp_common/mp2_common carry no database. An MP rifle (`US_rif_XM8c`) was
equally invisible.

- `sp02-m9-pistol.cfg` now also mounts `package:levels/mp_009sdm/level-00.fbrb` (15 MB patch bundle). Its
  `Dx11_Single` auto-registers with the Dx11ShaderSystem `[0x1572b18]`, and **the M9 draws in 1P**.
- The engine merges databases in registration order, with the last one winning same-named shaders.
  `BC2TestRange.dll` hooks RegisterDatabase (vtable slot `0x1448260` -> `0x9cb590`) so SP_02's own database stays
  last. It is on with mounts; `TestRange.ShaderOrder 0` turns it off.
- The banded sky and terrain in flat captures is pre-existing. It shows in a control run without the shader mount.
- Details and addresses: `WEAPON-LOADING-AND-DEBUG-RECOVERY.md` 1.6.

### Root cause of the `0xe93ed7` give fault (static RE; not yet applied)

- **The fault.** `0xe93ed7` is the `rep movsd` in constructor `0xe93ec0(this, aiData, const float[16]* src, owner)`.
  It copies 64 bytes from `src`, which is null.
- **The callers** (weapon-selected handlers in `0x5af790` at `0x5afb93`, and `0x58f520` at `0x58f5b0`):
  - take `sw=[item+4]` and `aiData=[sw+0xf0]` (`SoldierWeaponData.AIData`);
  - if `aiData` is set, look `src` up with `0x58ee90` (thiscall on the map `*(0x1567180)`, arg `sw`, `ret 4`).
    That returns node+0x14, or 0 on a miss, and nothing checks it.
- **The map** is an AI weapon ballistics cache filled by `0x5a5a00(sw)` (stdcall, `ret 4`).
  The loader walk `0x5ac4c0` registers only the weapons reachable from loaded soldier, pickup, cutscene or component data.
- **Why these guns.** The G3 and Mk14EBR Kobra/Scoped variants (and Binoculars) have AIData but are never registered.
  The bases are probably reachable from loaded entity data; this is not proven.
- **Fix, before the give:**
  1. If `[sw+0xf0]` is set and `0x58ee90(*(0x1567180), sw)` returns 0, null-check `sw+0x98` (WeaponFiring) and its
     `+0x40` / `+0xe4` / `+0xf0` / `+0x1d0`.
  2. Call `0x5a5a00(sw)`.
  3. Look up again, and give only if the lookup is non-null.
  4. Otherwise skip the gun.

### Resolved (2026-10-10 20:05)
- **`0xe93ed7` fixed.** `EnsureAiCache` runs before each give: if `[sw+0xf0]` is set and `0x58ee90` misses, it
  calls `0x5a5a00`. The signatures were verified with REA. In the sweep it registered 15 variants
  (G3, Mk14EBR, Neostead/USAS FRAG, M95 Frag and others).
- **Sweep coverage.** A full sweep of all 305 guns turned up two more faults, and both are now handled:
  - `MEC_shg_TOZ194*` has no async bundle, and the arsenal now skips such data;
  - `NAM_Handgrenade` faults at `0x8ac396` and is excluded by default.
- **Order.** The rotation opens with the physical-reload guns.
- **Evidence.** VAs are recorded in `docs/re/bc2-foreign-weapon-loading.md`.
